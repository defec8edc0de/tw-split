# Threat model

Public GitHub Pages repo => the adversary can read every file, all history and all timestamps, and may serve modified files (compromised CDN, repo write access, a hostile page on the same `*.github.io` user origin).

## Security rests on one password

Everything hangs off a single random 256-bit key (the DEK). The DEK is stored **only** inside the stage-1 `tw.html`, in a stock TiddlyWiki/SJCL blob (PBKDF2-HMAC-SHA256 -> AES-128-CCM, 64-bit tag). That file is public, so an attacker has a perfect **offline** guessing oracle (the CCM tag). Per-tiddler AES-256-GCM adds nothing against someone who guesses the password: the password yields the DEK, the DEK yields every file, every historic revision in git, and every future one.

* `migrate` writes the blob with `--kdf-iter` PBKDF2 iterations (default **300 000**, about 1.3 s in a browser). TiddlyWiki's own decryptor reads the iteration count from the blob, so this works with the unmodified core; stock TiddlyWiki uses 10 000. Rough, order-of-magnitude attacker speed with GPUs: ~10^6 guesses/s per GPU at 10 000 iterations, ~3x10^4/s at 300 000. A 4-word Diceware passphrase (~52 bits) then costs on the order of a GPU-year; 6 random words (~77 bits) or 16+ random characters are out of reach. **Use a long random passphrase (>= 6 Diceware words).** Anything you can remember as a "password" is not enough.
* **The old wiki's password is already burned.** The old whole-wiki ciphertext sits in the public repo's history and is exactly as guessable as before. If you reuse the old password for the new stage-1 blob you gain nothing against an attacker who saved the old file. Run `migrate` with `TW_NEW_PASSWORD` set to a fresh strong passphrase (never published anywhere before). The tool warns when both are equal.
* AES-128 vs 256 in the blob is irrelevant (the password is the weak point); the 64-bit CCM tag only means a wrong guess passes with probability 2^-64.
* Password change / key rotation: there is no way to revoke a published key. `twmigrate.py rotate` creates a new random DEK, re-encrypts every file under new opaque names, and writes a new stage-1 blob (optionally under a new password). It protects **future** content only: the old DEK (and the old password) keep opening everything already in git history, forks and caches. After rotating you must also purge the old files from the repository history (orphan branch / force-push) and accept that anything already cloned or cached stays readable. The in-page "Set password" button is disabled on purpose (the page never rewrites stage-1, so it would silently change nothing).
* Forgetting the password = losing everything (the DEK exists nowhere else). Keep an offline `inline` backup (`twmigrate.py inline`) of your data, which is a classic encrypted single-file wiki.

## Protected

Tiddler titles, text, tags, fields, media, categories, exact sizes (bucket padding), and integrity/authenticity of every **data** file and of the manifest (AES-GCM; file<->title<->revision binding; hashes in the manifest), *given that the stage-1 code you run is genuine* (see below).

## Not protected / residual

* **Stage-1 itself is unauthenticated code.** Whoever can change `tw.html` (repo write access, GitHub Pages/CDN compromise, a malicious same-origin page that swaps it) controls the code that receives your typed password and the GitHub token. Nothing in this design (no SRI, no signature - the user can only verify what they already trust) prevents that; GCM protects the data files only against an attacker who does not control stage-1. Treat repo write access as full compromise.
* Number of files per category folder (folder names are keyed HMACs, but anyone can list the directories, so the *distribution* of notes over categories is visible), number of files and rough sizes (`m/` manifest size too), commit times/frequency, which file changed in which commit (a note's file id is stable, so its edit history/frequency is visible), which notes change together.
* Everything ever committed stays in history: deleted or edited notes remain decryptable with the DEK. There is no forward secrecy.
* Which TiddlyWiki plugins are installed: every tiddler with a `plugin-type` field **and a `$:/` title** goes in plaintext into stage-1 (gzip makes this about 1 MB). `migrate` prints that list; a personal plugin containing private text would be published. Non-system tiddlers that merely carry a `plugin-type` field stay encrypted (and `migrate` warns).
* The rest of the original HTML skeleton is copied as-is and was never encrypted: page `<title>`, raw-markup tiddlers, customised `$:/boot/boot.css` and `$:/boot/boot.js`, `data-tiddler-creator/modifier` attributes. Read the top and bottom of `out/tw.html` before publishing; `verify` only scans stage-1 for the *text* of your notes and the key.
* A repo writer can roll the whole repo back to an older consistent state (the client warns if the manifest counter decreases vs. what this browser has seen; a fresh browser cannot tell). Availability (delete everything) is likewise unprotected.
* Weak password: see above.

## Browser side

* The GitHub token is entered through TiddlyWiki's Control Panel and kept by TiddlyWiki core in `localStorage` (`tw5-password-github`) in stock TiddlyWiki; this plugin moves it to `sessionStorage` by default (`$:/config/ext/enc/TokenStorage` = `memory`|`session`|`local`) and migrates an existing localStorage copy away. Use a **fine-grained token limited to this single repository (Contents: read/write)** - the origin also serves other pages of the same user site; any XSS there can read it. The token is only sent as `Authorization: Bearer` to the configured API base and never logged.
* **Key handling after unlock.** The boot kernel decrypts the bootstrap blob into the wiki store and into `$tw.preloadTiddlers` (a global that lives as long as the page). At startup the adaptor deletes the DEK tiddler from **both**, derives non-extractable `CryptoKey`s, zeroes the byte array, and then drops TiddlyWiki's in-memory password (`$tw.crypto.setPassword(null)`, and makes it impossible to set again). Without that, any script in the page could call `$tw.crypto.decrypt()` on the still-present blob and read the DEK, and a stock whole-wiki save would re-encrypt the loaded store under the password. Limits: JavaScript strings cannot be wiped (the base64 DEK, the decrypted JSON and the typed password stay in the heap until garbage collection; a heap dump or a browser extension reads them); `$tw.encSync` (the engine) is global, so any script running in the page can still read or write every note and use the token - but can no longer obtain the DEK itself, which is what would let it read old git history and future content.
* TiddlyWiki's syncer logs tiddler titles to the browser console (`Dispatching 'save' task: ...`). That stays local, but do not paste console output anywhere.
* Saving: the stage-1 file is never re-saved. `Save` (Ctrl+S, cloud button) commits pending encrypted changes through the GitHub Git Data API. The saver guard has top priority, so the stock GitHub/download/put savers can never overwrite `tw.html` with a half-loaded wiki; if the engine failed to start it refuses to save at all. Whole-wiki *download* ("save a copy") is refused (it would contain only already-loaded tiddlers, in plaintext now that the password is gone); selected-tiddler exports (JSON/CSV/.tid/static) still work and are decrypted by design - they are your copies to protect. Use `twmigrate.py inline` for a full backup.
* Decrypted content is in page memory and can be exported by the user, as always in TiddlyWiki.
* **Local save targets.** The `zip` target and the `folder` target only ever write what the repository would hold anyway: AES-GCM ciphertext files, the encrypted manifest and `_remove.txt` (a list of opaque `<12hex>/<32hex>.bin` paths). No plaintext, no key, no token, no titles ever enter a zip or the folder (tested: the zips contain no plaintext and no token). The browser download folder and any synced folder (Dropbox, OneDrive, …) now hold the same ciphertext as the public repo (same metadata exposure: file count, sizes in buckets, timing); `tw.html` (stage-1, with the password-protected key blob) is not written by the plugin.
* **File System Access handle.** The directory handle of the wiki folder is stored in IndexedDB (database `tw-enc-sync`, key `tw-enc-sync/folder-handle`) of the page's origin. It grants nothing by itself: Chrome re-checks the permission (`queryPermission`), `showDirectoryPicker`/`requestPermission` are only called from an explicit Save click (never from timers or autosave), and the sink refuses to write unless the folder holds `tw.html` or this wiki's manifest (an empty folder only after confirmation), writes only paths of the fixed shape `[<base>/](<12hex>/<32hex>.bin|m/<32hex>.bin)` and never deletes anything else (`tw.html` and your other files are safe). Any script running in the page (same trust domain as the token, see above) can drive the already-permitted sink and therefore write/delete **ciphertext files in that one folder**; it cannot read your other files or write outside the chosen folder. In Chrome, web storage of `file://` pages is generally shared between all local files, so other local HTML files you open may be able to read that IndexedDB entry and the localStorage anti-rollback counters (not verified here); treat the folder permission as being granted to every `file://` page you open with relaxed file access. Revoke it in Chrome's site settings (or clear site data) if you stop using the folder target.
* **Anti-rollback and local saves.** The rollback floor is derived only from counters observed on the remote/page over http(s) or produced by our own successful commits; the counter bump of a local save is not trusted (a `file://` copy could be an old or tampered folder) and cannot trigger or suppress a refusal. Consequence: a repository that is *behind* a locally-ahead state is overwritten by Publish (that is the purpose), and an attacker who can edit your local folder can make Publish push *their* state to GitHub, exactly as they could with the stock single-file wiki; a repository that is behind what this browser has *seen on GitHub* is still refused. A deleted/missing repository manifest after a counter was seen is refused too (`acceptRollback()` to override).
* **Zip limits.** The zip is built in memory (store only, no zip64): refused above 1.5 GiB or 65 535 files, with a clear message.

## Migration tool

* Passwords only via environment (`TW_PASSWORD`, optional `TW_NEW_PASSWORD`), never argv or files; each variable is removed from the process environment as soon as it is read (child processes do not inherit it). Python strings cannot be wiped; the shell history and `ps e` of an interactive session are your responsibility (prefer `read -rs TW_PASSWORD; export TW_PASSWORD` or a one-off `TW_PASSWORD=... cmd` that your shell does not record).
* The DEK comes from the OS CSPRNG (`os.urandom` via pycryptodome), 32 bytes. SJCL salt (8 bytes) and IV (16 bytes) are fresh random per encryption; the CCM nonce is the first 15-L bytes of the IV with L chosen exactly as in `sjcl.mode.ccm` (checked against the real `sjcl.js` of TiddlyWiki 5.1.21 in `tests/test_migrate.py`, including the 64 KiB length-of-length boundary). Blob parameters are range-checked on decryption; plaintext is released only after the CCM tag verifies.
* `out/` contains plaintext only in `tw.html`: the system plugins/themes/languages and this plugin's source. Everything else is `.bin` ciphertext.


## Browser-side hardening (web pentest wave)
* **Message guard:** core's `window` `message` listener would add any posted tiddler to the wiki (and the adaptor would then encrypt and commit it). A capturing listener drops every message that is not from the plugin-library iframe the core itself created.
* **Active HTML filter:** `srcdoc` and `javascript:` attribute values are dropped, `base/meta/link/applet/frame/frameset` are made inert, `javascript:` links/forms are blocked on click/submit. Opt out with `$:/config/ext/enc/AllowActiveHtml` = `yes`. `text/html` tiddlers stay in a `sandbox=""` iframe.
* **Alerts/errors** are shown literally (`<$text>`), never as wikitext; GitHub error text is sanitised.
* **Skinny-save guard:** a metadata change on a not-yet-loaded tiddler first loads its text, so a note can never be overwritten with an empty body.
* **Stage-1 head:** `referrer: no-referrer` and a frame-busting guard (the only anti-clickjacking option on GitHub Pages). Optional `migrate --csp` adds a Content-Security-Policy (script hashes, `connect-src 'self'` + the API origin); it breaks external images/iframes and the online plugin library.
* **Network:** redirects are refused (the token never follows a redirect), responses are size-capped while streamed and time-limited, GitHub rate limits are honoured with back-off, tree paths can only be `<12hex>/<32hex>.bin` or `m/<32hex>.bin` (the repo's `tw.html`, `index.html`, `CNAME`, `assets/` can never be written or deleted), and commits are refused (not silently merged) when the repo's manifest counter is below what this browser has seen.
* **Still open:** any script that runs in the page (XSS elsewhere on the same origin, a malicious browser extension) can use `$tw.encSync` and the token; stylesheet tiddlers synced from the repo are applied (CSS exfiltration is only blockable with `--csp`); two devices editing the *same* tiddler concurrently resolve as last-writer-wins.

## Publishing (plaintext blog posts)

`publish.js` / `publish-ui.js` let you turn a note into a **public** Markdown post of the website that shares the repository (Hugo: `content/blog/<slug>/index[.de].md`). This is deliberate disclosure; the controls exist to prevent *accidental* or *induced* disclosure:

* **Opt-in per tiddler**: only tiddlers tagged `publish:blog`, only from the *publish post* button (or the status bar under a tagged note). On an untagged note the button first asks (native dialog) whether to add the tag; adding it publishes nothing. Never from timers, autosave, Save, or *Publish to GitHub now*.
* **Consent gate the page cannot fake**: the preview modal shows the exact bytes; the final step is a native `window.confirm()` (wikitext can send `tm-enc-post-confirm`, but cannot answer a native dialog). The preview is single-use, held in a closure (not in a tiddler), and the post is rebuilt from the live tiddler and must be byte-identical to what was previewed.
* **Nothing else leaks in**: transclusions (`{{…}}`, `{{{…}}}`), macros, widgets, pragmas, raw HTML and TiddlyWiki image/ext-link syntax are refused (code spans/blocks may contain them). `[[links]]` to tiddlers that are not published become plain text, so private titles appear only if you wrote them as text. Vault tags are never copied (only `publish-tags`). Media: image tiddlers referenced in the post text (`![alt](#Title)`, `[img[Title]]`) or listed in `publish-media`, PNG/JPEG/WebP only; external image URLs are refused.
* **Invisible/bidi Unicode is refused** (tag characters U+E0000–E007F, zero-width, BOM, bidi controls): hidden prompt-injection or "trojan source" text cannot ride along in a post. The website's build refuses it too.
* **Separate allowlist, separate commit**: post files must match `content/blog/<slug>/(index(.de)?.md|<name>.(webp|png|jpe?g))`; `commitPlain()` refuses ciphertext paths and `commit()` refuses post paths, so plaintext and ciphertext are never in one commit.
* **Front matter is JSON-quoted** (valid YAML): titles cannot inject keys or break out of the front matter. The site renders Markdown with raw HTML disabled.
* **Conflicts**: the git blob id of the last publish is kept in `publish-sha`; if the post was edited elsewhere (github.dev), publishing refuses unless you confirm an overwrite.

Residual risks:

* Whatever you confirm is public, and stays in git history (and caches, forks, archives) after *unpublish*.
* **Timing correlation**: the publish commit and the next encrypted save of the same tiddler (which records `publish-slug`/`publish-sha`) happen close together, so an observer can link the post to *one* opaque ciphertext file id and watch its later edit frequency. It reveals nothing about other notes.
* The page is one trust domain: a script running in the wiki page (see "Browser side") could drive the publisher like any other API and show you a misleading preview text — but it cannot pass the native confirm dialog for you.
