# Deploying (you do the git steps; the tools never touch the repository)

1. Choose the password of the NEW stage-1 file: a long random passphrase (>= 6 Diceware words) that has never been published; it is the only thing protecting the key to every note (see THREAT-MODEL). Then, without putting either password in your shell history or in a file:
   `read -rs TW_PASSWORD; read -rs TW_NEW_PASSWORD; export TW_PASSWORD TW_NEW_PASSWORD` (old wiki password, then the new passphrase), run `migrate` + `verify` (see README; add `--kdf-iter N` to trade unlock time for guessing cost, default 300000), then `unset TW_PASSWORD TW_NEW_PASSWORD`. Output: `out/`. Reusing the old password works (leave `TW_NEW_PASSWORD` unset) but protects nothing the old public ciphertext does not already expose.
   Look at the `PLAINTEXT in stage-1` list printed by `migrate`: those plugins/themes become public.
2. In your Pages repo clone: replace `tw.html` with `out/tw.html` and copy the opaque folders and `m/` from `out/` next to it (do **not** delete `index.html`, `assets/`, …).
3. `git add -A && git commit && git push`. Wait for the Pages deployment, open the wiki, unlock it, check a few notes/images.
4. Enter your token once in *Control Panel → Saving → GitHub* (fine-grained, repo-only: select this repository, **Contents: read and write**, **Metadata: read**). Edits now commit automatically (`Update`), or press the cloud button / Ctrl+S.
5. Keep `backup/original-tw.html` somewhere safe and **private** (it contains your old ciphertext). The old `tw.html` is still in the repo's git history and guessable with the OLD password; purging it (orphan branch + force-push) only helps against people who have not already copied it.
5a. Key/password rotation: `TW_PASSWORD=<current stage-1 password> TW_NEW_PASSWORD=<new> twmigrate.py rotate --out out --dest out2` (new random key, every file re-encrypted under new names, new stage-1). Replace the repo contents with `out2/`, **and** purge the old files from history; whatever was ever published remains readable with the old key. Changing the password inside the wiki (Control Panel) is deliberately disabled.
6. Installing/updating TiddlyWiki plugins: they live in stage-1; re-run `migrate` on a wiki that includes them (or ask for the `add-plugin` helper). Changes to plugin tiddlers are rejected by the adaptor on purpose.
7. After you see other devices' changes only after reload (no live polling by design).

## Local-first workflow (run `tw.html` from a folder, publish to GitHub when you want)

Typical case: a synced folder such as `C:\Users\you\Notes\wiki\` holds `tw.html`, the opaque folders (`<12 hex>/`) and `m/`, you open `tw.html` with `file://` (Chrome with `--allow-file-access-from-files`, otherwise the browser refuses to read the neighbouring files), and the same files are also published on GitHub Pages.

* **Save targets** are chosen by the tiddler `$:/config/ext/enc/SaveTarget`, a comma list of `github`, `folder`, `zip` (spaces/case do not matter, unknown words are ignored, blank = default). Default: opened from `file://` -> `folder` (`zip` if the browser lacks the File System Access API, i.e. everything but Chromium); opened from `http(s)` -> `github`. You can edit it in the app; it takes effect immediately.
* **Ctrl+S / Save / the cloud button** write to *all* configured targets, in the order GitHub, folder, zip. A failing target never stops the others; the first error is shown at the end.
* **`folder`**: the first Save shows Chrome's folder picker: choose the folder that contains `tw.html` (a folder with neither `tw.html` nor this wiki's manifest is refused; an empty folder only after you confirm). The permission is remembered (IndexedDB + Chrome's persistent permissions); if Chrome has forgotten it, the next *explicit* Save asks again. The background timer (a few seconds after you stop typing) writes to the folder silently, but only if the permission is already granted; it never opens a dialog. Encrypted files are written first, the manifest last, deletions after that, so an interrupted save leaves the previous consistent state.
* **`zip`** (fallback / manual): every Save downloads `tw-update-<counter>.zip` containing every changed or new encrypted file at its relative path, the new manifest `m/<id>.bin`, and `_remove.txt` (paths to delete, one per line; present even if empty). It is never created from the timer. To apply it: extract it over the wiki folder (overwrite), then delete the files listed in `_remove.txt`, e.g. in PowerShell `Get-Content _remove.txt | ForEach-Object { Remove-Item -LiteralPath $_ -ErrorAction SilentlyContinue }` (run it in the wiki folder, then delete `_remove.txt` itself), or in a POSIX shell `xargs -d '\n' rm -f < _remove.txt`. Apply the zips **in order and do not skip one**: each contains only what changed since the previous save. If you lose one, extract a "full" copy from GitHub or run `$tw.encSync.saveLocal($tw.encTargets.sinks.zip,{full:true})` in the browser console (one zip with every file). A zip counts as saved once the browser started the download.
* **Publish to GitHub now** (second button in the page controls, message `tm-enc-publish`) makes the repository match your local state regardless of `SaveTarget`: it reads the repository's manifest, and
  * if there is none (404 on the manifest: a fresh repository, `out/` never deployed) or the repository's manifest counter is lower than yours, it *fast-forwards* the repository to your local state in **one commit**: every local file whose hash differs from (or is missing in) the repository is uploaded, every repository file your wiki no longer has is deleted (only paths named by the repository's own authenticated manifest; `tw.html`, `index.html`, `CNAME`, ... are never touched). **You do not copy the `.bin` files by hand**: seeding uploads them from your local folder. Only the stage-1 `tw.html` still has to be copied/committed by you (the plugin never writes it).
  * if the repository's counter is equal or higher (someone/another device published meanwhile) it only overlays what you changed since opening and keeps the other side's work.
  * if nothing differs, no commit is created; pressing it again is a no-op.
* **Counters.** Every local save (folder or zip) and every commit raises the manifest counter. The anti-rollback check only trusts counters that were observed from GitHub / the page over `http(s)` or from your own successful commits, so saving locally never makes a later publish look like a rollback; a repository whose manifest counter is *below* what this browser has seen is still refused (run `$tw.encSync.acceptRollback()` in the console if you really restored an older repository).
* **One writer at a time.** The local folder is the master: "local counter higher than the repository's" means "overwrite the repository with mine". Do not edit the same wiki from two devices without publishing/reloading in between (equal counters merge safely, but two devices that each made several unpublished local saves can overwrite one another's changes on GitHub). In local-first mode (a `folder` or `zip` target is configured) changes published by *other* devices are preserved in the commit but are not pulled into the open wiki (their files are not in your folder); reload from the GitHub Pages copy to see them.
* **Unsaved-changes warning on close** counts only enabled targets: unpublished edits matter only if `github` is a target; unsaved local edits only if `folder`/`zip` is. The page readme (plugin tiddler *readme*) shows "unsaved local changes / not yet published to GitHub".
* **First publish checklist**: (1) copy `out/tw.html` to the repository yourself and commit it, so the branch exists (an *empty* repository without any commit cannot be seeded through the Git Data API: GitHub typically answers `409 Git Repository is empty`), (2) token with Contents read+write and Metadata read for this repository only, (3) open the wiki from the local folder, press **Publish to GitHub now**. Error messages name the failing step (`read ref`, `read commit`, `read manifest at head`, `create blob`, `create tree`, `create commit`, `update ref`); GitHub reports a missing repository permission as `404 Not Found`, so a 404 on any step means: wrong repo/branch, or the token is not allowed to access *this* repository (fine-grained tokens must list it).

## Wiki in a sub-folder of the repository (`--repo-base`)

If `tw.html` should live in a sub-folder of the Pages repository, e.g. `vault/` next to a website, move `tw.html`, `m/` and the hex folders there together, then restage once:

```bash
TW_PASSWORD=… .venv/bin/python -I tools/twmigrate.py restage --out <repo>/vault --dest /tmp/tw.html --repo-base vault/
cp /tmp/tw.html <repo>/vault/tw.html
```

Encrypted files are still fetched relative to `tw.html`. Only the GitHub API paths (commits, the remote manifest) get the `vault/` prefix. **Don't save from an old `tw.html` after moving the folder:** without `repoBase` it would commit the encrypted files back to the repository root. `--repo-base ""` resets to the root.
